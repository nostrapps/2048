# NIP-133: Game Scores (Gamestr)

`draft` `optional`

This NIP defines a standard for publishing and querying game scores on Nostr.

## Abstract

Game scores are stored as parameterized replaceable events (kind 33334), allowing players to publish their high scores for various games. Each player can have one score per game, identified by a unique game identifier in the `d` tag.

## Event Format

### Kind 33334: Game Score

```json
{
  "kind": 33334,
  "content": "<score>",
  "tags": [
    ["d", "<game-identifier>"]
  ],
  "created_at": <unix timestamp>,
  "pubkey": "<player's public key>",
  "id": "<event id>",
  "sig": "<signature>"
}
```

### Fields

| Field | Type | Description |
|-------|------|-------------|
| `kind` | integer | Always `33334` |
| `content` | string | The score as a numeric string (e.g., `"2048"`) |
| `d` tag | string | Unique game identifier (e.g., `"2048-nostrapps"`) |
| `created_at` | integer | Unix timestamp when the score was achieved |

### Optional Tags

| Tag | Description |
|-----|-------------|
| `["r", "<game-url>"]` | URL where the game can be played |
| `["level", "<level>"]` | Level or stage reached |
| `["time", "<seconds>"]` | Time taken to achieve the score |
| `["verified", "<proof>"]` | Optional proof or verification hash |

## Game Identifier

The `d` tag MUST contain a unique identifier for the game. Recommended format:

```
<game-name>-<publisher>
```

Examples:
- `2048-nostrapps`
- `snake-example`
- `tetris-arcade`

## Querying Scores

### Fetch Leaderboard

To fetch all scores for a specific game:

```json
{
  "kinds": [33334],
  "#d": ["<game-identifier>"],
  "limit": 100
}
```

### Fetch Player's Score

To fetch a specific player's score for a game:

```json
{
  "kinds": [33334],
  "authors": ["<pubkey>"],
  "#d": ["<game-identifier>"]
}
```

## Behavior

### Replaceable Events

Kind 33334 is a parameterized replaceable event (NIP-01). When a player publishes a new score for the same game:

- Relays SHOULD replace the old event with the new one
- Clients MAY keep track of historical scores locally
- The `created_at` timestamp indicates when the score was achieved

### Score Ordering

Clients SHOULD:
- Parse `content` as an integer for comparison
- Sort scores in descending order (highest first)
- Handle invalid scores gracefully (non-numeric content)

### Deduplication

When querying multiple relays, clients SHOULD:
- Deduplicate by `pubkey` (one score per player)
- Keep the highest score if duplicates exist
- Use `created_at` as a tiebreaker if scores are equal

## Example

### Publishing a Score

```javascript
const event = {
  kind: 33334,
  content: "15832",
  tags: [
    ["d", "2048-nostrapps"],
    ["r", "https://nostrapps.github.io/2048/"]
  ],
  created_at: Math.floor(Date.now() / 1000)
}

const signedEvent = await window.nostr.signEvent(event)
```

### Leaderboard Query

```javascript
const filter = {
  kinds: [33334],
  "#d": ["2048-nostrapps"],
  limit: 50
}

// Query relays and sort results
const scores = events
  .map(e => ({ pubkey: e.pubkey, score: parseInt(e.content) }))
  .filter(s => !isNaN(s.score))
  .sort((a, b) => b.score - a.score)
```

## Security Considerations

### Self-Reported Scores

Scores are self-reported and signed by the player. This means:

- Players can publish any score they choose
- There is no server-side verification
- Trust is based on reputation and social verification

### Mitigation Strategies

Games MAY implement additional verification:

1. **Game State Hash**: Include a hash of the final game state
2. **Replay Data**: Store compressed move history for verification
3. **Time Validation**: Reject scores with suspicious timestamps
4. **Social Verification**: Display player reputation alongside scores

### Privacy

Players should be aware that:

- Scores are publicly visible on relays
- Their pubkey is associated with their gaming activity
- Historical scores may be preserved by relays or clients

## Recommended Relays

Games SHOULD publish to multiple relays for redundancy:

```javascript
const RELAYS = [
  'wss://relay.damus.io',
  'wss://nos.lol',
  'wss://relay.nostr.band'
]
```

## Player Identity

Clients SHOULD fetch player metadata (kind 0) to display:

- Display name or username
- Profile picture
- NIP-05 identifier if available

Link player profiles using the format:
```
did:nostr:<pubkey>
```

See [did:nostr specification](https://nostrcg.github.io/did-nostr/) for details.
